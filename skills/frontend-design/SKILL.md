# 前端设计：三条红线 + 案例教材 + 交付门

> v2 的教训（四组盲测实证）：规则对弱模型是拐杖，对强模型是镣铐；样例对两者都是营养。
> 所以这份文件只有三条红线。真正的教材在 references/——去读它，不是查阅它，是读它。
>
> v2.2 增补（2026-11）：把反复说过的道理变成可检查的东西——事实与资产、逐屏稿、外观账本、验收证据。规则仍然只有三条；多出来的是"查"，不是"限"：查的不是你有没有守规矩，是这次的设计有没有落在真实的产品上。

本文件提到的 `references/…`、`scripts/…` 都相对本 skill 根目录（SKILL.md 所在目录），不是用户的项目目录。

## 第 0 步：先判任务目标

同一个提示词，交付目标不同，评价轴完全不同。动手前先写下这次是哪一种：

| 任务 | 人类实际在评什么 | 打法 | 交付门 |
|---|---|---|---|
| **作品**（品牌 / 作品集 / 表达） | 概念是否长在名字里、每屏有没有自己的想法 | 三条红线全用；大胆 > 安全 | 零报错 + 逐屏截图链 + 作品自问 |
| **转化**（促销 / 投放 / 电商 / 海报） | 缩略图里能不能读出品牌 / 时间 / 产品 / 价格 | 允许退回商业配方，力气押在产品诱惑力与价格层级 | 缩略图门（300px）+ 事实核对 |
| **复刻**（照站 / 照图还原） | 像不像、全不全 | **红线②不适用**：还原（含使用参考素材）就是正确答案，原创反而扣分 | 像不像 / 全不全；题面清单逐条打勾 |
| **工具**（表单 / 看板 / 功能页） | 用起来是否不用解释 | 纪律派优先，场景化慎用 | 零报错 + 首屏可交互 + 可读性底线 |

判错的代价比画得差更大：作品题做安全 = 均值，复刻题做原创 = 零分，转化题做概念 = 好看但卖不动。

**第 0.5 步：事实与资产**（只在真实品牌 / 产品 / 事件时，几秒钟）。先把事实写下来再动手：`product-facts.md` 记页面每个数字 / 日期 / 版本的出处，`brand-spec.md` 记 logo 文件、色值出处、字体；凭记忆猜品牌色和发布状态 = 返工。详见 `references/facts-assets.md`。验收：每条事实有来源，每个色值有出处。

## 红线 1：无概念，禁止开工

写任何 HTML/CSS/JS 之前，先写出两句话：

```
这个概念是 ______
这个概念不是 ______
```

概念从产品的名字、行为、机制、领域文化里推导——不从风格库里选。"cyber 该用霓虹青"、"AI 产品该用深蓝紫"、"落地页该深色 hero" 都是风格库，是训练数据里最多的答案，不是推导。

把这两句话写进交付说明，不要只停在脑子里——它也是验收时判断"是不是套模板"的第一依据。

## 红线 2：参考站只学"为什么"

如果给了你参考（网站/视频/截图），分析它每个决策的理由——**禁止**复制它的配色、字体、布局、结构。概念可以撞，材质必须重新发明。照抄参考的决策结果是趋同的源头。

开工前先填这张表（三行就够，写进开工说明）：

| 它做了什么决策 | 为什么成立（放在它的产品/受众里） | 我借什么（机制 / 材质，不借外观） |
|---|---|---|
| 例：整页只有一个颜色 | 天气状态本身就是内容 | 借"一色一状态"的机制，颜色从我的题材重新采 |

**遮名测试**：把推导说明里的参考名遮掉，链条仍独立成立才算同构；否则是挪用（CASE-011 判据）。

## 红线 3：截图自验，以作品标准看

构建 → 截图 → 真的看图 → 修 → 再截图，循环到能交卷。看图时问一句："**这是作品还是作业？**"——作业通过规范就停；作品连规范没写的都做到了（favicon、footer 的性格、空状态、hover 的细节）。不可截图的项（声音/手感/旋律）诚实标注"未验证"，不许宣称完成。

**多屏设计先写逐屏稿**：页面 ≥5 屏或内容区块 >3 个时，先在 `screens.md` 排好每屏"讲什么 / 用什么形式 / 主角是谁"，相邻两屏不用同一种形式；每屏主角写不出来，就是还没设计。模板与形式菜单见 `references/screens.md`。

**验收要留证据**：逐屏截图（桌面 + 390 宽手机）+ `python3 scripts/quick_check.py 成品.html` 事实检查；把看了哪几张、修了什么写进 `verify.md`，只贴证据不写"已检查"。脚本只量事实（裂图 / 字号 / 占位残留 / 外链），不判断好不好看。详见 `references/verify.md`。

交付前两道硬门：

- **零报错门**：控制台无红色报错、首屏可交互。低分作品最常见的死法不是难看，是白屏（题库里真有 TDZ 报错整页白屏的低分作品）。
- **缩略图门**（转化任务）：把成品缩到 300px 宽，能读出「品牌 / 日期 / 产品 / 价格」才算过；读不出说明这是作品向的稿子，不许当投放稿交。

## 能力分档：先认清这次是哪一档

同一份教材，三种用法。分档只改"怎么做"，不改三条红线：

- **强档**（强模型 / 能看图 / 预算够）：按上面走，案例是弹药不是模板。发现自己逐条对规则、而不是在想产品该长什么样，就是进合规脑了。
- **弱档**（轻量模型 / 执行意愿低 / 上下文紧）：从案例或技法卡起步——抄推导路径，不抄色与壳；先写逐屏稿，再一屏一屏做，用清单验收。
- **无看图档**：截图交给用户看，自己跑 quick_check + 列"未验证项"，不许宣称看过。

降级要写在交付说明里：降了什么、为什么、哪里可能出问题。详见 `references/track.md`。

## 开工前查账本，交付后记一笔

- **开工前**：`python3 scripts/ledger.py recent` 看最近 8 次交付的底色 / 字体 / 骨架，写一句"这次要避开哪几样"——底色、强调色、字体、布局、动效、素材各是一个决策点（CASE-011：逃出强调色不等于逃出底色）。
- **交付后**：`python3 scripts/ledger.py add 成品.html --project 项目名` 记一笔。

账本只在本机（`~/.frontend-design/ledger.jsonl`），只记事实不打分，不禁止重复——重复是信息，"不知道自己在重复"才是问题。详见 `references/ledger.md`。

## 然后去读案例教材

**`references/cases.md`** —— 人工判决过的案例 + 对照观察（含 CASE-013 真实项目与站内同题池）。读法：

1. 找概念或题型与你相近的案例，读"**它敢了什么**"
2. 重点读"**同概念还有哪些答案没人选过**"——你的第一个答案大概率是训练数据里最多的那个（实测：四个模型组做同一道灯塔题，全部选了深色+琥珀）。说出你的第一答案，承认它，然后找第二个。第一答案不禁止——如果它确实是概念的最佳答案，那就用到比所有先验版本都狠
3. 别抄案例的样子，学案例的推导

**`references/technique-cards.md`** —— 14 个可复用的决策模式（立起时刻/仪式化开场/结构转译/…）。每张卡先看"同构性前提"：前提不满足，技法就是别人的衣服。

**`references/blacklist.md`** —— 均值识别指南 + 低分塌陷清单：单项技法不定罪，密度+无概念+均值化才定罪；作品被淘汰通常不是丑，是塌陷（跑不起来/缺段/错位/同构空转）。用于诊断，不用于禁令。

## 终止状态

交付 → 用户判决（过/不过+理由）→ 理由回写你自己的案例库（建议在工作目录下建 `design-lab/calibration.md`）；交付样子记进本机外观账本。

案例库比这份文件重要。它每次判决后生长，这份文件只是它的索引。
