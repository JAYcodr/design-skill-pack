# 能力分档：同一份教材，三种用法

> v2 的教训：规则对弱模型是拐杖，对强模型是镣铐；样例对两者都是营养。分档不是降低标准，是让"拐杖"只在需要时出现——强档别被流程吃掉注意力，弱档别从白纸开始硬憋。

## 先判档（看三件事）

1. **模型档**：能一次想出 2–3 个明显不同的概念（强档），还是倾向复述第一个答案（弱档：flash/haiku/mini/本地小模型）？
2. **有没有看图能力**：能打开截图并看出问题吗？
3. **预算**：时间/上下文够不够至少两轮"截图→改→再截图"？

三个都满足 = 强档；缺图或缺预算 = 降一档；弱模型直接按弱档起步，不丢人。

## 强档（默认）

- 按 SKILL.md 走：判题 → 概念两句话 → 参考拆解 → 构建 → 截图自验；
- 三条红线是底线不是上限，案例是弹药不是模板；
- 自检信号：发现自己在逐条对规则、而不是想"这个产品该长什么样"，已经进合规脑了——CASE-010 实证，协议把强模型从 85 拉到 70。

## 弱档

- **不从白纸开始**：找概念或题型相近的案例/技法卡，抄它的**推导路径**，不抄色与壳（遮名测试）；
- 先填参考拆解表，再写 `screens.md` 逐屏稿（references/screens.md），结构排对再写 CSS；
- 每屏只解决一个问题，用形式菜单挑形式，相邻不重复；
- 先做出 1 屏对的，再按同一套字号/颜色/间距复制到其余屏；
- 用 verify.md 的清单把"完成"拆成可勾的项；
- 判据：交付物不是"一百来行、小标题 + 三张卡片"那种骨架页。

## 无看图档

- 截图交给用户看；自己跑 `quick_check.py`，把硬伤清零；
- 交付说明列「未验证项」，不许宣称"看过/改过"；
- 概念仍然要写两句话，先让用户确认概念再谈实现——概念判断不依赖看图。

## 时间紧档

- 只做 1 个方向、1 轮打磨；
- 交付说明写"只打磨一轮 / 未做缩略图门 / 未验证声音"——不假装做过；
- 宁可少做一屏，不留占位和缺段。

## 降级原则

- 降"怎么做"，不降"概念是否成立"和"交付门"；
- 每次降级在交付说明写清：降了什么、为什么、哪里可能出问题；
- 出现这些信号，回退到弱档：两轮修改没变好 / 首屏三秒说不清 / 页面只有骨架 / quick_check 硬伤修不掉。

## 与"三条红线"的关系

分档只改工作方式，不改判断标准：无概念禁止开工、参考只学为什么、截图自验——三档都一样。强档可以比案例更狠；弱档至少要过案例的推导路径。
